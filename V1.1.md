# Tracewell V1.1: Fixes Before V2

V1 (Phases 0 to 7 of `PLAN.md`) is complete and described in `docs/V1.md`. This plan is a short cleanup release before V2 starts. It fixes a teaching problem in the N+1 scenario, closes gaps found in the V1 review, adds end-to-end tests, and deploys the app.

Do not start Phase 8 of `PLAN.md` until every step here meets its "Done when" criteria.

---

## Instructions for Claude

- Read `PLAN.md` (sections 1 to 5), `docs/V1.md`, and `docs/PROGRESS.md` before starting.
- Work through the steps in order. Stop after each step, run `pnpm test`, `pnpm lint`, `pnpm typecheck`, `pnpm build`, and log the step in `docs/PROGRESS.md` under a new "V1.1" heading.
- All rules from `PLAN.md` still apply: the engine never imports React, the UI never computes simulation results, everything is deterministic, costs come from `COST_CONFIG`.
- Do not tune `COST_CONFIG` values to hit a target number in this plan. If a result looks wrong, report it and ask.
- If a step needs something you cannot do here (for example, profiling in a normal desktop browser, or creating a GitHub repository), stop and ask the user.
- At the end, update `docs/V1.md` sections 11 and 12 so they match the code.

## Step 2: Engine fixes

### 2.1 Wrong method returns 404, like Express

The display code is Express, and Express answers 404 when the path exists under a different method.

- A path that matches only under another method returns 404 with body `{ "error": "Cannot <METHOD> <path>" }`, for example `Cannot DELETE /products/42`.
- Emit `ROUTE_NOT_FOUND` with a label that adds a hint, for example `No route for DELETE /products/42 (GET exists)`.
- Remove `METHOD_NOT_ALLOWED` and the `Allow` header.
- Update router tests and any product-api test that expected 405.

### 2.2 Error pointer points at the cause of the final status

Today `SimError.eventSeq` and `code` come from the last failed event, even when a handler caught that failure and returned a different status.

New rules:

- When a `DbError` is thrown into a handler at a `yield` and the generator continues normally (it caught the error), mark that event as handled. Add `handled?: boolean` to `SimEvent`, and append " (caught)" to its label.
- `SimError` for a response with status 400 or above points at:
  1. the failed event whose error reached the error handler, if there is one;
  2. otherwise the last failed event that is not handled (auth, validation, body parsing, routing);
  3. otherwise the `RESPONSE_SENT` event (for a 4xx the handler returned on purpose, like a 404 after an empty query).
- `code` comes from the event in rule 1 or 2. For rule 3, derive it from the status (`NOT_FOUND`, `CONFLICT`, `UNPROCESSABLE_ENTITY`, and so on).

Tests:

- A test handler that catches a 23505 and returns 422: the SQL event has `status: "fail"` and `handled: true`, and the error points at `RESPONSE_SENT` with code `UNPROCESSABLE_ENTITY`.
- An uncaught 23505 still gives 409 and points at the failed SQL event.
- `GET /products/999999` points at `RESPONSE_SENT` with code `NOT_FOUND`.

### 2.3 Cost breakdown on every SQL event

The UI must show why a query took its time, without computing cost itself.

- Add `cost` to `SqlInfo`:
  ```ts
  cost: {
    baseMs: number; // round trip, parse, plan
    scanMs: number; // rowsScanned * perRowScanMs
    sentMs: number; // rowsReturned * perRowSentMs
    writeMs: number; // rowsWritten * perRowWriteMs
    sortMs: number; // sort cost, 0 if no sort
  }
  ```
- Compute it in `engine/db/cost.ts` next to the duration, from the same numbers.
- Test: for several queries, the parts add up to `duration` within 0.001 ms.

Leave as is: `GET /products?limit=-1` reaching the database and returning 500. It will become a preset in the Phase 8 `pagination` scenario.

Done when:

- All new and updated tests pass.
- Running every product-api preset gives the same statuses as before, except wrong-method requests now give 404.

## Step 3: Separate N+1 from the missing index

### The problem

In the default `orders-n-plus-one` run, about 50 ms of the 1059 ms is round trips and about 1000 ms is seq scans of `order_items`, because `order_items.order_id` has no index. So the scenario mostly teaches "missing index", not "N+1". The real cost of N+1 is the number of round trips, which stays even with a good index.

### The change

Add a second fix, so the user can see both effects separately.

- New fix:
  - id: `indexOrderItems`
  - label: `Index order_items.order_id`
  - description: Postgres does not create indexes on foreign key columns automatically. This adds one.
- Let a scenario's `world` be either `TableDef[]` or `(fixes: Fixes) => TableDef[]`, the same pattern as `code`. `runSimulation` resolves it with the run's fixes. Keep seed data identical in both cases; only the index list changes.
- Show the schema change in the display code: when the fix is on, add a comment block at the top, for example:
  ```
  // Migration
  // CREATE INDEX order_items_order_id_idx ON order_items (order_id);
  ```
  Line numbers come from `lineOf`, so nothing else should need changing. Check that the tests for line numbers still pass.
- Update the scenario description to say it has two separate problems: N+1 round trips and a missing foreign key index.

### Expected shape (not exact numbers)

|                        | No index | Index       |
| ---------------------- | -------- | ----------- |
| N+1 (51 queries)       | slowest  | much faster |
| Eager load (2 queries) | fast     | fastest     |

Required in tests:

- All four combinations return exactly the same response body.
- N+1 with index is faster than N+1 without index.
- Eager load with index is faster than eager load without index, or equal if the orders query dominates; record which.
- N+1 with index is at least 3x slower than eager load with index. This is the point of the lesson. If the cost model does not produce this, stop and report the numbers instead of changing `COST_CONFIG`.
- Query counts: 51 for N+1, 2 for eager load, whatever the index setting.
- With the index on, the 50 item queries are Index Scans; without it, Seq Scans.

Record the four actual totals (time, rows scanned) in `docs/PROGRESS.md`.

Done when:

- All four combinations work in the UI and in tests.
- The comparison view shows the right differing fixes for any two of the four.

## Step 4: UI improvements

### 4.1 Cost breakdown in the inspector

On a `SQL_QUERY` event, under the existing SQL block, show the breakdown from `sql.cost`:

```
Round trip       1.000 ms
Rows scanned     4,000 x 0.005 = 20.000 ms
Rows returned    5 x 0.010 = 0.050 ms
Total            21.050 ms
```

- Hide lines that are zero (no write, no sort).
- Show the formula with the actual numbers so the user can see what drives the cost.
- Read the per-row constants from the engine (export `COST_CONFIG` or include them in the event). Do not copy them into UI code.

### 4.2 Keep the previous run automatically

Today, if the user forgets to pin a run, the comparison is lost.

- After every Run, the run that was on screen becomes A automatically, and the new run is B.
- "Pin" locks A. While A is pinned, new runs replace only B.
- "Unpin" returns to automatic mode.
- Label A as "Previous run" or "Pinned run" so it is clear which mode is active.
- Changing scenario clears both runs, as today.
- Comparison shows nothing until there are two runs.

### 4.3 Run summary next to the response

Next to the status in the response viewer, show total virtual time, SQL query count and rows scanned, from `result.metrics`. Shown at the same time as the response (when the cursor reaches the end).

### 4.4 Short "Why" panel per scenario

A short written explanation now, so step 8 of the V1 loop ("understand why the fix works") has support. The full learning layer is still Phase 10.

- Add `why?: string[]` to `Scenario`: a list of short paragraphs, 5 to 10 lines in total.
- Render as plain text paragraphs. Support inline code with backticks by splitting the string and rendering `<code>` elements. No Markdown library and no HTML rendering.
- Show it in a collapsible "Why" section under the scenario description in the header or above the request builder. Collapsed by default after the first visit is fine but not required.
- Write content for both scenarios:
  - `product-api`: what each pipeline stage is for, why auth runs before validation here, why an unknown error becomes a plain 500.
  - `orders-n-plus-one`: what N+1 is, why each query costs a round trip even when fast, why the index and the eager load fix different problems, and that ORMs cause this when lazy loading inside a loop.
- Keep the language plain. No em dashes.

Done when:

- All four items work in the browser at desktop and narrow widths.
- Unit tests cover the auto-keep logic (in `ui/compare/compare.ts` or a new logic file) and the backtick splitting.

## Step 6: Speed check

In V1, a Run click took 0.3 to 0.8 s in the headless test browser, while the simulation itself takes 1 to 3 ms in Node. This must be understood before Phase 9 adds multiple request lanes.

Tasks:

- Add a Playwright test (or a separate script) that measures, on the production build:
  - time from clicking Run to the first trace row being visible;
  - time for a single step (Right arrow) to update the position text;
    for both the Product API "Valid" preset and the default N+1 run. Log the numbers. Use loose assertions only (Run under 500 ms, step under 200 ms) so the test is not flaky.
- Ask the user to profile in normal desktop Chrome on the production build: Performance panel recording of one Run and five steps, and React DevTools Profiler with "Highlight updates". Ask them to share what they see.
- Likely causes to check if it is slow:
  - The whole `App` re-rendering on every cursor change.
  - The code panel re-tokenizing the code on every render (memoize by code string).
  - `formatJson` running on every snapshot of every event, not only the visible one.
  - Trace rows re-rendering when only the cursor changed.
- Fix only real problems found by measurement. Do not add memoization everywhere.

Done when:

- In normal desktop Chrome, Run feels instant (under 100 ms to first trace row) and stepping is under 50 ms, or the cause is found and written in `docs/PROGRESS.md` with a plan.
