## 1. What Tracewell V1 is

Tracewell is an interactive tool that shows what happens inside a backend server when it handles one HTTP request. It runs entirely in the browser. There is no real server and no real database: a simulation engine written in TypeScript models an Express-style Node.js server and a PostgreSQL database.

The user works through one loop:

1. Pick a scenario.
2. Edit a request (method, path, query params, headers, JSON body) or pick a preset.
3. Run it.
4. Step through the resulting trace one event at a time, or play it as an animation.
5. For each step, see the line of server code that is running, the request data at that moment, and any SQL that was executed, with its query plan and row counts.
6. Flip a fix toggle.
7. Run again.
8. Compare the two runs side by side.

V1 ships two scenarios:

| Scenario | What it teaches |
| --- | --- |
| Product API | The request pipeline itself: body parsing, routing, auth, validation, a database query, the error handler, the response. Nine presets cover the success and failure paths. |
| Orders: N+1 queries | An endpoint that runs 51 queries where 2 would do. The "Eager load items" fix brings it down to 2, and the comparison view shows the difference. |

### The V1 success test

Section 9 of the plan defines V1 as this loop working smoothly. It was walked in headless Chrome at the end of Phase 7:

| Step | Result |
| --- | --- |
| 1. Open the N+1 scenario | Scenario loads with its code, presets and one fix toggle |
| 2. Send `GET /users/1/orders` | 200 OK, 55 events, total virtual time 1059.083 ms |
| 3. Step through and see the 51 queries with the code line highlighted | The 50 item queries collapse into one row, "50× SELECT order_items", which shows "11 of 50" while stepping and expands to 50 rows. The code panel highlights the query inside the loop |
| 4. Switch to play mode and watch it | Animates through the group quickly |
| 5. Turn on "Eager load items" | Checkbox in the Fixes box; a notice says to run again |
| 6. Run again and see 2 queries | 200 OK, 6 events, 30.083 ms. The code panel shows the `IN (...)` version |
| 7. Compare both runs side by side | See the table below |
| 8. Understand why the fix works | Only by reading the code change and the numbers. There is no written explanation yet (that is Phase 10) |

| | A (default) | B (with fix) | Change |
| --- | --- | --- | --- |
| Status | 200 OK | 200 OK | same |
| Total time | 1059.083 ms | 30.083 ms | −97% |
| SQL queries | 51 | 2 | −96% |
| Rows scanned | 201,000 | 5,000 | −98% |
| Rows returned | 249 | 249 | same |

All times in Tracewell are virtual. They come from a cost model, not from measuring anything. See [the cost model](#74-cost-model).

## 2. Running and checking it

The project uses pnpm. Node 20.18.1 was used throughout.

```
pnpm install
pnpm dev         # start the app, then open the printed URL
pnpm test        # run all tests once
pnpm test:watch  # run tests on change
pnpm lint        # ESLint, including the engine import guard
pnpm typecheck   # tsc --noEmit
pnpm build       # typecheck, then a production build into dist/
pnpm preview     # serve the production build
```

All of `test`, `lint`, `typecheck` and `build` pass at V1. The build prints two harmless Rollup warnings about comments inside Zod.

### Checking it by hand

In the browser (`pnpm dev`):

1. **Product API, each preset.** Click a preset, then Run. Expected statuses: Get product 200, List by category 200, Valid 201, Missing field 400, Invalid value 400, Not found 404, No token 401, Wrong role 403, Duplicate name 409.
2. **Index scan against seq scan.** Run "Get product" and "List by category". Click the `db` row in each and look at the inspector: the first is an Index Scan over 11 rows, the second a Seq Scan over 1,000.
3. **Invalid JSON.** Delete a closing brace from the body of "Valid". A warning appears under the editor. Run it anyway: the server answers 400 at the parsing stage.
4. **Missing content type.** Remove the `Content-Type` header from "Valid" and Run. The body is skipped and validation fails.
5. **Player.** Run "Valid" and let it play. Press Space to pause, use the arrow keys to step, Space again to resume. Change the speed while it plays.
6. **Code and data flow.** Run "Invalid value", switch the inspector to "Data flow", and step to the validation event. The rest of the route's code is dimmed, and the data flow list shows Raw body, Parsed JSON and "Validation failed", with no Validated DTO.
7. **The N+1 loop.** The eight steps in the table above.
8. **Narrow window.** Below about 960 px the layout stacks into one column with no sideways scroll.
9. **Reduced motion.** Turn on "Reduce motion" in the operating system's accessibility settings and reload. The app opens in step mode and the moving dot is gone.

From the terminal:

- `pnpm vitest run --reporter=verbose` lists every tested behaviour by name.
- Add `import React from "react";` to the top of `src/engine/index.ts` and run `pnpm lint`. It must fail with "The engine must not import React". Remove the line afterwards.

## 4. Architecture

```
Scenario data (world, routes, handlers, display code, presets, fixes)
        |
        v
Engine (pure TypeScript, no React)
        |
        v
SimulationResult (events + responses + metrics + errors + final table rows)
        |
        v
UI (renders the events at a cursor position)
```

### 4.1 The seven principles, and how V1 meets them

| Principle from the plan | How V1 implements it |
| --- | --- |
| The engine decides what happens. The UI only displays it | UI files import only `runSimulation`, `createRequest`, `statusLabel`, `scenarioCode` and types from the engine. ESLint stops the engine importing React or UI code |
| Everything the user sees is driven by the event log | Trace, pipeline strip, code panel, inspector, data flow, response and comparison all read `result.events` or values derived from it |
| The simulation is deterministic | Same scenario, request, fixes and seed give a deep-equal result. Randomness only through a seeded RNG (mulberry32). Tested |
| Time is virtual | The engine has its own clock in milliseconds. ESLint bans `Date.now`, `Math.random`, `setTimeout` and `setInterval` in engine and scenario files |
| The database is real data in memory | Queries filter and sort real row arrays. Results are never made up |
| Costs come from work done | Duration is computed from rows scanned, returned, sorted and written. All constants are in one object, `COST_CONFIG`, labelled as model parameters |
| Handlers are generator functions that yield effects | True for handlers, middlewares and the request pipeline itself |

### 4.2 One generator per request

A handler is a generator function. It yields **effects** (small objects that describe work, such as "run this query"). The engine runs the effect, records an event, advances the virtual clock, and resumes the generator with the result.

```ts
export const getProduct: Handler = function* (ctx) {
  const id = Number(ctx.req.params.id);
  if (!Number.isInteger(id)) {
    return ctx.res.status(400).json({ error: "Invalid product id" }, { line: lines.invalidId });
  }
  const rows: Row[] = yield db.select("products", { where: { id } }, { line: lines.selectById });
  if (rows.length === 0) {
    return ctx.res.status(404).json({ error: "Product not found" }, { line: lines.notFound });
  }
  return ctx.res.json(rows[0], { line: lines.sendProduct });
};
```

From Phase 3 on, the whole request is a single generator, `requestPipeline`. It yields the events for the request arriving, body parsing and routing, then runs each middleware and the handler inside itself with `yield*`, catches anything they throw (this is the error handler), and yields the response event. The runner only ever drives one generator per request. That is what will let the Phase 9 scheduler interleave several requests by stepping their generators in turn, without rewriting the pipeline.

### 4.3 Display code is separate from behaviour

Each scenario has a string of Express-style JavaScript, the **display code**. It is shown in the code panel and is never executed. The real behaviour is in the generator handlers. Every effect carries a `line` number pointing into the display code. Line numbers are not hard-coded: `lineOf(code, snippet)` finds the one line containing a snippet and throws if there are zero or several, so editing the display code cannot silently break the highlighting.

### 4.4 State at cursor

The UI holds one **cursor**, an index into the event list. Everything renders the state at that position: events after the cursor are dimmed, the code panel highlights the cursor's line, the data flow view shows only data produced so far, and the response appears only once the cursor reaches the end. Play mode moves the cursor on a timer; step mode moves it on demand.

## 6. Phase by phase

Each phase lists its goal, what was built, how its "Done when" criteria were verified, and the decisions made where the plan left something open.

### Phase 0: Project setup

**Goal:** an empty project with guardrails in place.

**Built**

- Vite + React + TypeScript app managed with pnpm, strict mode on.
- Vitest with a passing sample test.
- ESLint flat config. `no-restricted-imports` blocks `react`, `react-dom`, their subpaths, and anything under a `ui` folder for files in `src/engine` and `src/scenarios`.
- The folder structure from section 4 of the plan, with placeholder `index.ts` files.
- `docs/PROGRESS.md` with a phase checklist.
- Scripts: `dev`, `build`, `test`, `lint`, `typecheck`, plus `preview` and `test:watch`.

**Verified**

- `test`, `lint`, `typecheck` and `build` all passed.
- Temporary files in `src/engine` and `src/scenarios` importing `react` and `../ui/layout` made lint fail with four errors. The files were removed afterwards.

**Decisions**

- Tool versions held back for Node 20.18.1 (see [Tech stack](#3-tech-stack)).
- pnpm was not installed on the machine and corepack's bundled copy failed signature verification, so pnpm was run through `npx pnpm@10.34.6` without changing the global setup.
- The `ui` import block is a regex on the import path, so the engine also cannot have its own folder named `ui`.
- The lint guard has no lasting automated test. It was checked by hand and should be rechecked if `eslint.config.js` changes.

### Phase 1: Engine core

**Goal:** an engine that runs a generator handler, records events and returns a `SimulationResult`. No database yet.

**Built**

- The core types.
- Virtual clock (`now`, `advance`), starting at the request's `startAt`.
- Seeded RNG (mulberry32) with `next()` and `int(min, max)`. Handlers reach it through `ctx.rng`. The seed is stored in the result.
- Event recorder with an incrementing `seq`, starting at 0.
- Effect runner: drives the generator, runs effects, resumes with results, catches thrown errors.
- Effects `delay(ms, label, line)` and `log(label, line)`.
- Step limit of 10,000 effects per simulation.
- `runSimulation` for a single request.

**Verified by tests**

- Three yielded effects give three events in order with correct virtual times.
- The same input twice gives deep-equal results; a different seed gives a different result.
- An infinite loop of yields stops at the step limit with an `ENGINE_STEP_LIMIT` error result.

**Decisions**

- Every failure ends the run with an error event, a `SimError` and a 500 response.
- `runSimulation` throws if it is not given exactly one request. Multiple requests arrive in Phase 9.
- Lint rules banning `Date.now`, `Math.random`, `setTimeout` and `setInterval` in engine and scenario files were added. This was not in the plan's task list.
- The step limit counts yielded effects. A handler that loops forever without yielding would still freeze the page. Handlers are written by the project, so this is a rule for scenario authors and not a runtime guard.

### Phase 2: Simulated PostgreSQL

**Goal:** an in-memory database that behaves like Postgres for the cases the product needs.

**Built**

- Table model: name, columns (name, type, nullable), primary key, unique columns, indexed columns, rows.
- Structured query objects, with no SQL parser: `select`, `insert`, `update`, `delete`, with `where`, `orderBy`, `limit`, `offset` and `columns`.
- SQL text generator producing display SQL with `$1, $2` params.
- Query execution against real rows.
- Cost model, with all constants in one config object.
- `SQL_QUERY` events carrying text, params, plan, rows scanned and rows returned.
- Constraints: NOT NULL (23502) and unique (23505), surfaced as a typed `DbError` that handlers can catch.
- Effects `db.select`, `db.insert`, `db.update`, `db.delete`.

**Verified by tests**

- On 1,000 rows, select by an indexed column is an Index Scan over 11 rows; by a non-indexed column a Seq Scan over 1,000.
- Insert with a duplicate unique value fails with 23505 and writes nothing.
- Generated SQL matches expected strings for all four statement types.
- The same query twice gives the same cost.

**Decisions**

- Writes behave like `RETURNING *`: every db effect resumes the handler with rows, and the display SQL ends with `RETURNING *`.
- An integer primary key left out of an insert is filled from a per-table sequence, like `SERIAL`. A failed insert does not use up an id.
- Only equality and `IN` on an indexed column use an index. Range comparisons and NULL checks always seq scan. Primary key and unique columns are indexed automatically.
- Indexes are declared columns that change the plan and the cost. Rows are still found by filtering the real row array, so there is no separate index data structure.
- A failed query still records a `SQL_QUERY` event, with `status: "fail"` and the error in its snapshot.
- Keys and indexes are single-column only.
- The handler generator's resume type is `any`, because TypeScript cannot type each `yield` separately. Handlers annotate results: `const rows: Row[] = yield db.select(...)`.
- Bad seed data throws a plain `Error` when the database is created. It is a scenario bug, not a simulated failure.

### Phase 3: HTTP request pipeline and first scenario

**Goal:** a request goes through a realistic Express-style pipeline and produces a response.

**Built**

- Request model and JSON body parsing. Invalid JSON becomes a 400 at the parsing stage.
- Router with method and path patterns (`/products/:id`). No match gives 404; a wrong method gives 405 with an `Allow` header.
- Middleware chain. Middlewares are generators and can end the request early.
- Validation middleware using a Zod schema, answering 400 with one message per field.
- Auth middleware with a fake JWT (base64 JSON, no crypto): missing or unreadable or expired gives 401, wrong role gives 403.
- Error handler mapping thrown errors to statuses: 23505 to 409, anything unknown to 500.
- Response builder.
- Scenario registry and the `product-api` scenario.

**Verified by tests**

| Request | Result |
| --- | --- |
| `GET /products/42` | 200, one SQL event, no errors |
| `GET /products/999999` | 404 after a DB event |
| `POST /products` without a token | 401, no DB event |
| `POST /products` with `price: -5` | 400, no DB event |
| `POST /products` with a duplicate name | 409 |

A further test checks that every event points at the display code line doing that work.

**Decisions**

- `SimRequest.body` became the raw body text. The engine must parse it for invalid JSON to fail at the parsing stage.
- The body is parsed only when `Content-Type` contains `application/json`, like `express.json()`. Header names are case-insensitive.
- A middleware that returns a response ends the request; returning nothing passes it on.
- Auth and validation reject by returning a response after a failed event. Thrown errors go to the error handler.
- `result.errors` has one entry for every response with status 400 or above, including a 404 a handler returns on purpose. Its `code` and `eventSeq` come from the last failed event.
- Token expiry is checked against a fixed simulated date, never the real one.
- The invalid JSON message is a fixed string, because the parser's own message differs between JavaScript engines.
- Snapshots are deep-copied when recorded, so they keep the data as it was at that moment.
- All durations are rounded to 0.001 ms.

### Phase 4: UI shell, request builder, trace list

**Goal:** a usable screen to run the first scenario. No animation yet.

**Built**

- Header with a scenario picker fed by the registry.
- Request builder: preset buttons, method select, path input, query params table, headers table, JSON body editor, Run button.
- Inline JSON parse warning before running.
- Trace list: one row per event with a status symbol, stage, label, virtual start time and duration.
- Inspector: label, status, stage, event type, times, code line, SQL block, snapshot JSON.
- Response viewer: status, total virtual time, headers, body, and the error with a link to the event where it went wrong.
- Responsive layout that stacks on narrow screens. Light and dark themes through `prefers-color-scheme`.

**Verified in headless Chrome against the dev server**

- Every preset was clicked and run and showed the expected status and trace.
- A hand-typed `GET /products?category=audio&limit=3`, an unknown path (404) and a wrong method (405) worked.
- No console errors. At 390 px wide the layout is one column with no horizontal scroll.
- UI files import only `runSimulation`, `createRequest`, `statusLabel` and types from the engine.

**Decisions**

- Invalid JSON shows a warning but does not block Run, because the 400 at the parsing stage is something to learn from.
- Picking a preset loads it and clears the run on screen. Editing any field deselects the preset.
- Pressing Enter in the path field runs the request.
- A query string typed into the path works as well as the query params table.
- Status is shown with a symbol and screen reader text, never colour alone.
- No UI test library was added. UI behaviour is checked in a real browser; the logic that shapes user input into a request (`draft.ts`) has unit tests.

### Phase 5: Player (step mode and animation mode)

**Goal:** the user chooses how to move through the trace: step by step, or as an animation.

**Built**

- `usePlayer(events, reducedMotion)` with `cursor`, `mode`, `speed`, `granularity`, `next`, `prev`, `first`, `last`, `seek`, `play`, `pause`, `toggle`.
- Player controls: First, Prev, Play / Pause / Replay, Next, Last, position, mode, speed (0.5x, 1x, 2x, 4x), step granularity.
- Pipeline strip with a dot that moves in play mode.
- Trace: events after the cursor dimmed, current row highlighted and kept in view.
- Event grouping: consecutive events with the same `groupKey` collapse into one expandable row.
- Keyboard: Left and Right step, Space plays or pauses, Home and End jump.
- `prefers-reduced-motion`: opens in step mode and hides the moving dot.

**Verified in headless Chrome**

- Switching modes mid-run keeps the cursor: paused at event 3, it stayed at 3; Next moved to 4; Play resumed from 4.
- Changing speed during play works without restarting: switching to 4x at event 2 kept the cursor at 2 and kept playing.
- With reduced motion, the app opens in step mode and stays on the first event after Run.

**Decisions**

- The mode is kept between runs. Any manual move switches to step mode. At the end of a trace, Play becomes Replay.
- The response viewer shows the response only when the cursor is on the last event.
- "Step by stage" stops on the last event of each run of same-stage events, so a stage's work is complete at every stop.
- Keys are ignored while typing in a field. Space pressed on a button outside the trace presses that button.
- The current trace row is kept in view by scrolling the trace panel only, never the page.

### Phase 6: Code panel and data flow view

**Goal:** the user sees which line of code is running and how the data changes.

**Built**

- Code panel showing the display code with line numbers and light syntax highlighting (keywords, strings, numbers, comments). No editor library.
- Highlight of the line for the event at the cursor, kept in view.
- "Not reached" styling for code after a failure.
- Data flow view in the inspector: a vertical list of Raw body, Parsed JSON, Validated DTO, SQL params, DB row, Response body. Each appears only once the cursor reaches it.
- A switch in the inspector between "This step" and "Data flow".
- Engine change: a successful `SQL_QUERY` event's snapshot now holds the first 5 rows the query returned.

**Verified by tests and in headless Chrome**

- Stepping through `POST /products` highlights lines 7, 40, 42, 43, 47, 50 in order: body parser, route, auth, validate, INSERT, 201 response.
- A validation failure shows Raw body and Parsed JSON, then "Validation failed", then the response, and no Validated DTO.

**Decisions**

- "Not reached" applies to the matched route's own code. After the first failed event at or before the cursor, every non-blank line of that route after the last line that ran is dimmed and its number struck through. A 404 the handler returns on purpose counts. A failure before routing marks nothing.
- Long code lines wrap instead of scrolling sideways.
- A later query replaces the SQL params and DB rows of an earlier one in the data flow list. A failed step shows the failure in place of its data.
- The inspector uses two switch buttons, not ARIA tabs, so the arrow keys keep stepping the player.
- The right column became code panel above inspector.

### Phase 7: Fix toggles, comparison, N+1 scenario (V1 milestone)

**Goal:** the first complete learning loop.

**Built**

- Fix toggle system. A scenario declares `fixes` (id, label, description). Handlers read `ctx.fixes.<id>`. Display code can be a function of the fixes.
- The `orders-n-plus-one` scenario.
- Comparison view: pin a run as A, run again as B, and see status, total time, SQL queries, rows scanned and rows returned side by side, with the change and the fixes that differ.
- Metrics module computing those numbers from events only.

**Verified by tests and in headless Chrome**

- Default run: 51 queries. With the fix: 2 queries and lower total time, with exactly the same response body.
- The comparison shows both runs with correct numbers.
- Tests cover both variants, including that each variant's events point at the right lines of its own code.
- The section 9 loop was walked in the browser (see [the V1 success test](#the-v1-success-test)).

**Decisions**

- Both code variants share the same text up to the orders query, so the lines the pipeline uses do not move between them.
- Toggling a fix does not clear the run on screen. The code panel keeps showing the code that run used, and a notice says to run again. This keeps a run available to pin.
- B is always the run on screen once it differs from A. The comparison covers whole runs, not state at the cursor.
- Every metric in the comparison is "lower is better", so a drop is marked as an improvement with an arrow as well as colour.
- Playback: events of the same group are 140 ms apart at 1x, and the longest pause dropped from 3000 ms to 1800 ms.

## 7. Engine reference

### 7.1 Entry point

```ts
runSimulation({ scenario, requests, fixes?, seed? }): SimulationResult
```

- `requests` must hold exactly one request in V1.
- `fixes` defaults to `{}`; `seed` defaults to 1.
- Each call builds a fresh database from `scenario.world`, so runs never affect each other or the seed data.

```ts
type SimulationResult = {
  requests: SimRequest[];
  responses: Record<string, SimResponse>; // keyed by request id
  events: SimEvent[];
  metrics: Metrics;      // totalTime, sqlQueries, rowsScanned, rowsReturned
  errors: SimError[];    // one per response with status >= 400
  worldAfter: WorldSnapshot; // every table's rows at the end of the run
  seed: number;
};
```

### 7.2 Events

```ts
type SimEvent = {
  seq: number;        // global order, from 0
  requestId: string;
  stage: Stage;
  type: string;
  label: string;      // short text for the trace
  startTime: number;  // virtual ms
  duration: number;   // virtual ms
  line?: number;      // display code line
  status: "ok" | "fail" | "skip" | "wait";
  snapshot?: unknown; // data at this moment, deep-copied
  sql?: SqlInfo;
  groupKey?: string;  // consecutive events with the same key collapse in the trace
};
```

Event types in V1:

| Stage | Types |
| --- | --- |
| `network` | `REQUEST_RECEIVED` |
| `middleware` | `BODY_PARSED`, `BODY_PARSE_SKIPPED`, `BODY_PARSE_FAILED` |
| `router` | `ROUTE_MATCHED`, `ROUTE_NOT_FOUND`, `METHOD_NOT_ALLOWED` |
| `auth` | `AUTH_OK`, `AUTH_MISSING_TOKEN`, `AUTH_INVALID_TOKEN`, `AUTH_TOKEN_EXPIRED`, `AUTH_FORBIDDEN` |
| `validation` | `VALIDATION_OK`, `VALIDATION_FAILED` |
| `controller` | `DELAY`, `LOG` |
| `db` | `SQL_QUERY` |
| `error` | `ERROR_HANDLED`, and the engine aborts `ENGINE_STEP_LIMIT`, `ENGINE_INVALID_EFFECT`, `ENGINE_INTERNAL_ERROR` |
| `response` | `RESPONSE_SENT` |

The stages `pool`, `lock` and `eventloop` exist in the type but nothing emits them until Phase 9.

A successful request to `POST /products` produces, in order: `REQUEST_RECEIVED`, `BODY_PARSED`, `ROUTE_MATCHED`, `AUTH_OK`, `VALIDATION_OK`, `SQL_QUERY`, `RESPONSE_SENT`.

Engine aborts stop the simulation itself. They record no `RESPONSE_SENT` event.

### 7.3 Effects

| Effect | Creates | Resumes the handler with |
| --- | --- | --- |
| `delay(ms, label, line?)` | A `DELAY` event that takes `ms` of virtual time | nothing |
| `log(label, line?)` | A `LOG` event of zero duration | nothing |
| `trace({ stage, type, label, status?, code?, ms?, snapshot?, line?, groupKey? })` | One event at any stage. Used by the pipeline and middlewares | nothing |
| `db.select(table, query?, meta?)` | A `SQL_QUERY` event | the matching rows |
| `db.insert(table, values, meta?)` | A `SQL_QUERY` event | the inserted row, in an array |
| `db.update(table, { set, where? }, meta?)` | A `SQL_QUERY` event | the updated rows |
| `db.delete(table, { where? }, meta?)` | A `SQL_QUERY` event | the deleted rows |

`meta` is `{ line?, label?, groupKey? }`. A failed query throws a `DbError` into the handler at the `yield`, so `try`/`catch` works as it would with a real driver.

### 7.4 Cost model

All constants live in `COST_CONFIG` in `src/engine/core/config.ts`. **They are model parameters chosen to make the shape of the work visible. They are not benchmarks of a real Node.js or PostgreSQL server.**

| Constant | Value (virtual ms) | Meaning |
| --- | --- | --- |
| `requestMs` | 0.1 | Accept the connection and read the headers |
| `bodyParseMs` | 0.05 | Parse a JSON body, plus `perJsonKbMs` per KB |
| `routeMs` | 0.02 | Match a route |
| `authMs` | 0.05 | Check a token |
| `validationMs` | 0.05 | Validate a body |
| `responseMs` | 0.1 | Send a response, plus `perJsonKbMs` per KB of body |
| `perJsonKbMs` | 0.02 | Per KB of JSON parsed or serialized |
| `baseMs` | 1 | Database round trip, parse and plan |
| `perRowScanMs` | 0.005 | Per row scanned |
| `perRowSentMs` | 0.01 | Per row returned |
| `perSortCompareMs` | 0.002 | Multiplied by `n * log2(n)` for a sort of `n` rows |
| `perRowWriteMs` | 0.1 | Per row written |

Query duration:

```
duration = baseMs
         + rowsScanned  * perRowScanMs
         + rowsReturned * perRowSentMs
         + rowsWritten  * perRowWriteMs
         + (rowsSorted > 1 ? rowsSorted * log2(rowsSorted) * perSortCompareMs : 0)
```

Rows scanned:

- **Seq Scan:** the size of the table.
- **Index Scan:** `ceil(log2(n))` per lookup key, plus the rows the index points at. A lookup by primary key in 1,000 rows scans 10 + 1 = 11.
- **Insert:** `ceil(log2(n))` per unique column checked.

A sort cost applies when the first `orderBy` column has no index.

Every duration is rounded to 0.001 ms.

### 7.5 Database

**Supported**

- `WHERE` conditions combined with AND: equality, `ne`, `in`, `gt`, `gte`, `lt`, `lte`, `IS NULL`, `IS NOT NULL`. Comparisons against NULL are never true, as in SQL.
- `ORDER BY` on one or more columns, ascending or descending. NULLs sort last when ascending.
- `LIMIT`, `OFFSET`, and a column list.
- NOT NULL and unique constraints on insert and update. A rejected write changes nothing.

**Error codes**

| Code | Meaning | Default HTTP status if uncaught |
| --- | --- | --- |
| 23502 | NOT NULL violation | 500 |
| 23505 | Unique violation | 409 |
| 42P01 | Unknown table | 500 |
| 42703 | Unknown column | 500 |
| 2201W | Negative or non-integer LIMIT or OFFSET | 500 |

**Not supported:** OR, joins, aggregates, column defaults other than the serial primary key, type checking of values, multi-column keys or indexes, transactions, locks, a connection pool.

### 7.6 HTTP pipeline

In order:

1. **Request received.** Header names are lowercased.
2. **Body parsing.** Skipped when there is no body or the content type is not JSON. Invalid JSON ends the request with 400.
3. **Routing.** First matching route wins. 404 when no path matches, 405 when the path matches under another method.
4. **Middlewares**, in the order the route lists them.
5. **Handler.**
6. **Error handler**, for anything thrown in steps 4 or 5.
7. **Response sent.**

What handlers and middlewares receive:

```ts
type HandlerContext = {
  req: HttpRequest; // id, method, path, params, query, headers, rawBody, body, user?
  res: ResponseBuilder; // res.status(code).json(body, { line }) and res.json(body, { line })
  fixes: Fixes;
  rng: Rng;
};
```

Error handler mapping:

| Thrown | Status | Body |
| --- | --- | --- |
| `HttpError(status, message, code?)` | its status | `{ error: message }` |
| `DbError` with code 23505 | 409 | `{ error: "Resource already exists", detail }` |
| Any other `DbError` | 500 | `{ error: "Internal Server Error" }` |
| Anything else | 500 | `{ error: "Internal Server Error" }` |

Unknown errors never leak their message to the client. The message is still recorded in the event and in `result.errors`.

### 7.7 Scenario definition

```ts
type Scenario = {
  id: string;
  name: string;
  description?: string;
  world?: TableDef[];
  routes: Route[];                 // { method, path, middlewares?, handler, line? }
  code?: string | ((fixes: Fixes) => string);
  lines?: { bodyParser?: number; errorHandler?: number };
  presets?: Preset[];              // { id, label, description?, request }
  fixes?: Fix[];                   // { id, label, description }
};
```

## 8. Scenario reference

### 8.1 Product API (`product-api`)

**Tables**

- `products (id, name, price, stock, category)`: 1,000 rows built from a formula, so the data is identical on every load. `id` is the primary key, `name` is unique, and `category` has no index. Product 42 is "Lunar Toaster". Categories: kitchen, office, outdoor, audio, lighting.
- `users (id, email, role)`: 3 rows. Not read by any route.

**Routes**

| Route | Middlewares | Behaviour |
| --- | --- | --- |
| `GET /products/:id` | none | 400 for a non-integer id, 404 when not found, otherwise the product |
| `GET /products?category=&limit=` | none | Up to `limit` products (default 20), ordered by id, optionally filtered by category |
| `POST /products` | `requireAuth({ role: "admin" })`, then `validateBody(schema)` | Inserts a product, answers 201 |

The body schema is `name` (non-empty string), `price` (positive number), `stock` (non-negative integer), `category` (non-empty string).

**Presets**

| Preset | Request | Status | Events | Total virtual time |
| --- | --- | --- | --- | --- |
| Get product | `GET /products/42` | 200 | 5 | 1.287 ms |
| List by category | `GET /products?category=audio&limit=5` | 200 | 5 | 6.278 ms |
| Valid | `POST /products` as admin | 201 | 7 | 1.584 ms |
| Missing field | `POST /products` without `price` | 400 | 6 | 0.373 ms |
| Invalid value | `POST /products` with `price: -5` | 400 | 6 | 0.374 ms |
| Not found | `GET /products/999999` | 404 | 5 | 1.271 ms |
| No token | `POST /products` with no `Authorization` | 401 | 5 | 0.323 ms |
| Wrong role | `POST /products` with a user token | 403 | 5 | 0.323 ms |
| Duplicate name | `POST /products` named "Lunar Toaster" | 409 | 8 | 1.474 ms |

This scenario has no fix toggles.

### 8.2 Orders: N+1 queries (`orders-n-plus-one`)

**Tables**

- `users (id, name, email)`: 20 rows.
- `orders (id, user_id, status, created_at)`: 1,000 rows, 50 per user, interleaved across users.
- `order_items (id, order_id, product, quantity, unit_price)`: about 4,000 rows, with 3, 4 or 5 items per order decided by the order id.

Only primary keys are indexed. Nothing indexes `orders.user_id` or `order_items.order_id`, so every lookup by those columns reads the whole table.

**Route:** `GET /users/:id/orders` returns the user's orders, each with its items.

**Default behaviour (the bug)**

1. `SELECT * FROM orders WHERE user_id = $1 ORDER BY id`: one query, 50 rows.
2. For each order, `SELECT * FROM order_items WHERE order_id = $1`: 50 queries, each a Seq Scan over 4,000 rows.

That is 51 queries, 201,000 rows scanned, 1059.083 ms. The 50 loop queries share the `groupKey` `order-items`.

**With the "Eager load items" fix**

1. The same orders query.
2. `SELECT * FROM order_items WHERE order_id IN ($1, ..., $50)`: one query.

That is 2 queries, 5,000 rows scanned, 30.083 ms, and exactly the same response body.

**Presets:** "User with 50 orders" (`GET /users/1/orders`) and "User with no orders" (`GET /users/999/orders`, which runs a single query and returns an empty list in both variants).

### 9.3 Player behaviour

- **Modes.** Play mode moves the cursor on a timer. Step mode waits. Play mode is the default unless reduced motion is set.
- **Mode persists between runs.** In play mode a new run animates from the first event; in step mode it waits there.
- **Any manual move switches to step mode:** the buttons, the arrow keys, clicking a trace row.
- **Animation gap** between two events: the virtual time between their starts times 600, kept between 450 ms and 1800 ms, divided by the speed. Events of the same group are 140 ms apart.
- **Step granularity.** "Every event" moves one event at a time. "Stage" stops on the last event of each run of same-stage events.

## 12. Known limits and open questions

Updated for V1.1 on 2026-10-07.

### Engine

- One request per simulation. No concurrency, transactions, locks, connection pool or event loop model.
- The step limit counts yields. A handler that loops forever without yielding would freeze the page.
- `LIMIT` without `ORDER BY` still scans the whole table in a seq scan. Real Postgres would stop early.
- No type checking of column values.
- `GET /products?limit=-1` reaches the database, fails with 2201W, and comes back as a 500. Left on purpose: it becomes a preset in the Phase 8 `pagination` scenario.

### UI

- Toggling a fix does not change the code panel until the next run.
- The data flow view shows only the most recent query's params and rows.
- Nothing is saved across page reloads.
- The "Why" text for the N+1 scenario says an indexed item query takes "about 1 ms". That figure comes from the cost model, so the sentence needs checking if `COST_CONFIG` changes.

### Tooling

- **Node 20.18.1 is past its end of life** (April 2026). V1.1 set out to move off it and did not, by the user's decision. Vite, `@vitejs/plugin-react` and ESLint cannot be upgraded until Node is at least 20.19 or 22.12, and Vitest 5 needs 22.12 or 24. ESLint 9 prints a "no longer supported" warning on install.
- The CI workflow has not been run on GitHub. The action versions in it (`actions/checkout@v4`, `pnpm/action-setup@v4`, `actions/setup-node@v4`, `actions/upload-artifact@v4`) are unverified against what GitHub currently supports.
- Vite's `base` is the default `/`. A deployment under a sub-path, such as GitHub Pages at `/Tracewell/`, needs `base` set to that path.

### Deployment

- The app is not deployed by this project. The user deploys it manually. `README.md` has no live link yet.

### Speed

- Measured on the production build in Playwright's headless Chromium: Run to first trace row takes about 2 ms (Product API) and 5.5 ms (N+1, 55 events); a step takes about 1 ms.
- The 0.3 to 0.8 s Run reported in V1 was an artefact of the browser environment used for checking then. It does not reproduce.
- Still open: nobody has confirmed the feel in a normal desktop Chrome. The measurement stops when the DOM is updated and does not include painting the frame.

### Resolved since V1

- The error entry pointing at a failed query the handler had already caught.
- A wrong method giving 405 where Express gives 404.
- The comparison losing the earlier run when the user forgot to pin.
- Query and row counts being visible only in the comparison.
- The lint import guard having no automated test.
- Step 8 of the V1 loop, "understand why the fix works", having no written support.
- pnpm not being installed.

### Environment notes

- macOS file names are case-insensitive. `dataFlow.ts` and `DataFlow.tsx` in one folder broke the typecheck in Phase 6. Do not create files whose names differ only by case.
- First use of the end-to-end tests on a machine needs `pnpm exec playwright install chromium`.
