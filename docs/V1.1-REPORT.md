## 1. Summary

V1.1 had four aims: fix a teaching problem in the N+1 scenario, close gaps found in the V1 review, add end-to-end tests, and deploy the app.

**Three of the four were met.**

- **The N+1 scenario now teaches N+1.** In V1, about 1000 ms of its 1059 ms came from a missing index, not from the 51 round trips. A second fix now adds that index, so the two problems can be seen separately. With the index on, N+1 is still 4.5 times slower than eager loading (63.078 ms against 14.078 ms), which is the lesson the scenario is for.
- **The review gaps are closed.** A wrong method now answers 404 like Express. An error points at its real cause. Every query shows where its time goes. The previous run is kept for comparison without pinning. Each scenario has a short written "Why".
- **The UI has repeatable tests.** 14 Playwright tests replace the one-off browser scripts used during V1.
- **The app was not deployed.** The user chose to deploy it manually. A CI workflow was written but has not run on GitHub.

Two other things did not go as planned:

- **Node was not upgraded.** The user chose to stay on Node 20.18.1, which reached end of life in April 2026. Most tool upgrades were blocked by that.
- **The speed concern from V1 turned out not to be real.** Run takes 2 to 6 ms and a step about 1 ms. The slow numbers in V1 came from the browser environment used for checking. One confirmation in desktop Chrome is still outstanding.

Everything passes locally on Node 20.18.1: 163 unit tests, 14 end-to-end tests, lint, typecheck and build. Nothing from V1.1 has been committed.

## 4. Step 2: Engine fixes

### 4.1 A wrong method returns 404, like Express

The display code is Express, and Express answers 404 when a path exists only under another method. V1 answered 405.

- `DELETE /products/42` now answers 404 with body `{ "error": "Cannot DELETE /products/42" }`.
- The trace event is `ROUTE_NOT_FOUND` with a hint: `No route for DELETE /products/42 (GET exists)`.
- `METHOD_NOT_ALLOWED`, the 405 and the `Allow` header are removed.
- Beyond the plan: a path that matches nothing at all uses the same body shape, `Cannot GET /nope`, because Express sends the same text in both cases.

### 4.2 The error pointer points at the cause of the final status

In V1, the error entry for a failed request came from the last failed event, even when the handler had caught that failure and returned something else.

- A query error that the handler catches and recovers from is marked `handled: true` on its event, and its label gets " (caught)".
- The error entry for a status of 400 or above now points at, in order:
  1. the failed query whose error reached the error handler;
  2. otherwise the last failed event the handler did not recover from (auth, validation, body parsing, routing, a thrown error);
  3. otherwise the `RESPONSE_SENT` event, with a code taken from the status: `NOT_FOUND`, `CONFLICT`, `UNPROCESSABLE_ENTITY`, and so on.

Cases the plan did not cover, and what was chosen:

| Handler does this | Result |
| --- | --- |
| Catches a query error, then throws the same error again | The error did reach the error handler, so the query is the cause. Its "caught" mark is removed |
| Catches a query error, then throws a different error | The query stays marked as caught. The error points at the error handler |
| Catches a query error, then answers 200 | No error entry at all |

A small UI change followed: the code panel no longer dims the rest of a route after a failure the handler recovered from.

### 4.3 Cost breakdown on every SQL event

- Each SQL event now carries `cost` with `baseMs`, `scanMs`, `sentMs`, `writeMs` and `sortMs`.
- The duration is computed as the sum of those parts, so the two cannot drift apart.
- No `COST_CONFIG` value changed. Every timing assertion from V1 still passes.
- A failed query reports the cost of the work done before it failed.

### Verified

- The plan's three named tests exist: catch a 23505 and return 422; an uncaught 23505 giving 409 and pointing at the failed query; `GET /products/999999` pointing at the response with code `NOT_FOUND`.
- A new test confirms every Product API preset keeps the status it had in V1.

## 5. Step 3: Separate N+1 from the missing index

### The problem

In the default N+1 run, about 50 ms of the 1059 ms was round trips and about 1000 ms was sequential scans of `order_items`, because `order_items.order_id` had no index. The scenario mostly taught "missing index".

### The change

- A second fix: **Index order_items.order_id**. "Postgres does not create indexes on foreign key columns automatically. This adds one."
- A scenario's `world` can now depend on the fixes. With the fix on, `order_items` gets an index on `order_id`. The rows are identical in both cases.
- With the fix on, the display code starts with a migration comment:
  ```
  // Migration
  // CREATE INDEX order_items_order_id_idx ON order_items (order_id);
  ```
- The scenario description now says it has two separate problems, each with its own fix.

### The four totals for `GET /users/1/orders`

| | Queries | Total time | Rows scanned | Item query plan |
| --- | --- | --- | --- | --- |
| N+1, no index (default) | 51 | 1059.083 ms | 201,000 | Seq Scan, 4,000 rows each |
| N+1, with index | 51 | 63.078 ms | 1,799 | Index Scan, 15 to 17 rows each |
| Eager load, no index | 2 | 30.083 ms | 5,000 | Seq Scan, 4,000 rows |
| Eager load, with index | 2 | 14.078 ms | 1,799 | Index Scan, 799 rows |

What the numbers show:

- **N+1 with the index is 4.5 times slower than eager loading with the index.** The plan required at least 3 times.
- **An indexed item query takes 1.12 ms, of which 1 ms is the round trip.** Fifty of them cost about 56 ms that no index can remove.
- **Eager loading is faster with the index, not just equal:** 14.078 ms against 30.083 ms. The orders query takes 6.5 ms in every run and does not dominate.
- **N+1 with the index (63 ms) is slower than eager loading without it (30 ms).**
- All four return exactly the same response body.
- `COST_CONFIG` was not changed to reach these.

### One deviation from the plan's note

The plan said the migration comment would need no other change, because line numbers come from `lineOf`. That holds for the handler's lines. But the two lines the pipeline itself uses, the body parser and the route, were fixed per scenario, and the comment moves them down by 3. So `routes` and `lines` can now depend on the fixes too, the same pattern as `code` and `world`. A test checks that all four code variants point at the right text.

## 6. Step 4: UI improvements

### 6.1 Cost breakdown in the inspector

A SQL event has a "Where the time goes" table under its SQL block. For an N+1 item query:

```
Round trip                          1.000 ms
Rows scanned    4,000 x 0.005 =    20.000 ms
Rows returned       3 x 0.010 =     0.030 ms
Total                              21.030 ms
```

Zero lines are hidden. An INSERT adds a "Rows written" line. The amounts and the total come from the engine. The UI reads only the per-row constants, from the engine's `COST_CONFIG`, to print the formula.

### 6.2 The previous run is kept automatically

- Two runs with no pinning show a comparison. A is "previous run", B is "latest run".
- Each new run moves B to A.
- "Pin A" locks A. The heading becomes "A (pinned run)" and new runs replace only B. "Unpin A" returns to automatic.
- Changing scenario clears both runs.

Choices where the plan was silent: pinning with a single run locks that run as A, and picking a preset clears the trace on screen but keeps the comparison's runs.

### 6.3 Run summary next to the response

Under the status: total virtual time, SQL queries and rows scanned. For the default N+1 run that is 1059.083 ms, 51 and 201,000. It appears with the response, when the trace reaches its end.

### 6.4 A "Why" section per scenario

- A collapsible "Why" sits under the scenario description, closed by default.
- Four paragraphs for Product API: what the pipeline stages are for, why auth runs before validation, why validation runs before the handler, and why an unknown error becomes a plain 500.
- Five paragraphs for N+1: what N+1 is, why each query costs a round trip even when fast, why the two fixes solve different problems, a prompt to try each alone, and how ORMs cause it through lazy loading.
- Backticks become inline code. Nothing is rendered as HTML or Markdown.

The wording has not been reviewed by the user. The text is in `src/scenarios/product-api/index.ts` and `src/scenarios/orders-n-plus-one/index.ts`.

Also fixed in this step: a long duration such as `1051.99 ms` overflowed its column in a trace row.

## 8. Step 6: Speed check

### The measurement

`e2e/speed.spec.ts`, run with `pnpm test:speed`. It measures inside the page, on the production build, from the user's action until the DOM shows the result. It is a separate Playwright project with one worker, kept out of `pnpm test:e2e`.

| | Run to first trace row, median | First Run after page load | Step, median | Step, max |
| --- | --- | --- | --- | --- |
| Product API, "Valid" (7 events) | 1.8 to 2.0 ms | 6 to 7 ms | 0.9 to 1.0 ms | 1.7 ms |
| N+1, default run (55 events) | 5.4 to 5.6 ms | about 14 ms | 1.0 to 1.1 ms | 2.2 ms |

Three runs, Playwright's headless Chromium 153. The step's targets were Run under 100 ms and a step under 50 ms.

### The finding

The 0.3 to 0.8 s Run reported in V1 does not reproduce. That figure was measured in the system Chrome, driven by a script from inside a restricted tool sandbox, where all JavaScript ran slowly. A CPU profile there had shown the time spread evenly over every function, with no hot spot.

Nothing in the app was found to be slow, so nothing was changed. No memoization was added, and the four likely causes listed in the plan were not investigated.

### What is still open

The plan's criterion is about normal desktop Chrome. That has not been confirmed. The measurement is in headless Chromium, and it stops when the DOM is updated, so painting the frame is not included.
